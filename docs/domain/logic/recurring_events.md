# Recurring events

A recurring event must always have an explicit IANA timezone in `events.recurrence_timezone`.

Examples of valid values:

```text
Europe/Paris
America/New_York
Asia/Tokyo
```

Fixed offsets such as `UTC+1` must not be used as recurrence timezones because they do not describe daylight-saving transitions.

The default timezone proposed when creating a recurring event may be resolved from organization-level settings, but the resolved timezone must be copied into the recurring event itself.

Changing an organization or schedule setting must not implicitly change the timezone of an existing recurring event.

`events.recurrence_rule` contains only the recurrence pattern and its boundaries. The timezone and the initial local start and end are stored in dedicated columns.

## Changes to recurrence rules

Any change that alters the theoretical occurrence set must trigger an impact analysis before persistence.

Examples:

* changing weekdays;
* changing frequency;
* changing interval;
* changing the recurrence start;
* changing the recurrence boundary;
* changing the recurrence timezone.

The impact analysis must identify exceptions whose original occurrence is no longer generated by the new rule.

No incompatible exception may be silently migrated or deleted.

Initial resolution choices should be:

* cancel the recurrence-rule update;
* delete incompatible exceptions;
* convert modified incompatible exceptions into unique events.

A cancelled exception does not produce a unique event during conversion.

A modified exception converted into a unique event must materialize its final visible state, including inherited values and overrides.

The recurrence update, exception resolution and unique-event creation must occur in a single transaction.

Events and recurring-event occurrences become immutable once their effective end instant has passed.
Changes to recurring series apply only to future occurrences.

# Recurring Event Changes: Exception vs. Series Split

Changes to a recurring event must distinguish between modifying a **single occurrence** and modifying **multiple occurrences from a given point forward**.

## Single occurrence: use an exception

When a change applies to exactly one occurrence, the recurring series remains unchanged.

An `event_exception` targets the original occurrence through its original local start datetime.

Example:

```text
Series:
Every Monday, 08:00–10:00

Change:
Monday, September 14 → Wednesday, September 16, 14:00–16:00
```

The series still generates events every Monday.

An exception records that the specific occurrence originally scheduled for September 14 has been moved.

Conceptually:

```text
original_occurrence_starts_at_local = 2026-09-14 08:00
replacement_starts_at_local         = 2026-09-16 14:00
replacement_ends_at_local           = 2026-09-16 16:00
```

An exception therefore **does not define a new recurrence rule**. It overrides or cancels one specific occurrence generated by the existing rule.

## This occurrence and following occurrences: split the series

When a change applies from a specific occurrence onward, it must not be represented as an exception.

Instead, the recurring series is split into two series.

Example:

```text
Original series:
Every Monday, 08:00–10:00

Change from September 14 onward:
Every Wednesday, 14:00–16:00
```

The result is conceptually:

```text
Series A:
Every Monday, 08:00–10:00
Ends before September 14

Series B:
Every Wednesday, 14:00–16:00
Starts from September 16
```

The first series preserves the previous recurrence history, while the second series represents the new recurrence behavior.

Existing exceptions remain associated with the series whose occurrences they target.

## Rule

The distinction is therefore:

```text
One occurrence
→ Event exception

This occurrence and following occurrences
→ Series split

Entire series
→ Recurrence rule update, subject to impact analysis
```

Past occurrences must never be silently rewritten as a consequence of changing future recurrence behavior.

This keeps recurrence history stable and avoids using exceptions as substitutes for recurrence rules.
